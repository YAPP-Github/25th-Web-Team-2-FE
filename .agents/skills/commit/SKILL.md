# 변경사항 커밋하기

사용자가 커밋이나 작업 저장을 요청하거나 `/commit`을 직접 호출하면 이 스킬을 사용합니다.

1. 스테이징 전에 `git status`와 diff를 확인합니다. 요청된 작업에 포함되는 변경만 골라내고, 무관한 사용자 변경은 그대로 둡니다.
2. 변경을 목적별로 묶습니다. 사용자에게 보이는 결과나 기술적 목적이 다르면 커밋을 나누고, 서로 밀접한 구현과 필요한 UI 처리는 함께 커밋합니다.
3. 해당 커밋에 포함할 파일이나 hunk만 스테이징합니다. 무관한 변경이 있을 수 있으면 `git add -A`를 사용하지 않습니다.
4. 커밋 제목은 반드시 아래 허용 prefix 중 하나로 시작하는 `<prefix>: <변경 요약>` 형식으로 작성합니다. prefix 없는 커밋은 만들지 않습니다. 변경 목적에 맞는 가장 구체적인 prefix를 선택합니다.
5. 변경 내용을 설명하는 짧은 커밋 제목을 작성합니다. 테스트를 실행해 통과한 경우에만 통과했다고 기록합니다.
6. 커밋을 만든 뒤 커밋 목록과 worktree 상태를 확인합니다.
7. 사용자가 함께 요청하지 않았다면 push하거나 PR을 만들지 않습니다.

## 커밋 prefix

| Prefix | 사용 기준 |
| --- | --- |
| `feat` | 새로운 기능 구현 |
| `fix` | 기능이 잘못 동작하는 버그 수정 |
| `refactor` | 동작은 유지하면서 코드·폴더·이름·import 순서·포맷 개선 |
| `docs` | 문서 작업 |
| `chore` | `.gitignore`, YAML, ESLint, Prettier 설정 또는 라이브러리 설치 등 설정·유지보수 |
| `test` | 테스트 코드만 추가하거나 수정 |
| `design` | CSS 등 스타일링 변경 |
| `init` | 프로젝트 최초 설정 |
| `merge` | 로컬 충돌 해결 또는 PR 병합 |
| `assets` | 이미지·폰트 등 에셋 추가 또는 수정 |

구현과 테스트를 함께 변경하면 테스트 파일이 포함되어도 기능 변경의 목적에 맞춰 `feat`, `fix`, `refactor` 등을 사용합니다. `test`는 테스트 코드만 바뀌는 커밋에 사용합니다. 서로 다른 목적의 변경은 각 목적에 맞게 커밋을 나눕니다.

커밋 훅이 파일을 바꾸면 변경 내용을 확인합니다. 해당 커밋과 직접 관련된 포맷 또는 생성 결과만 포함하고, 그 외 변경은 멈춰서 사용자에게 알립니다.

완료 후 커밋 해시와 제목, 실행한 검증을 보고합니다.
